# Migrate from Pytincture 0.9 to 0.10

0.10 closes insecure implicit behavior. Treat the upgrade as a security and
packaging migration, not a drop-in dependency bump.

## Required review

1. Set a stable, random `SAML_SECRET_KEY` before enabling any authentication.
   `SECRET_KEY` remains a temporary fallback but should be renamed.
2. Replace allowlist-only email login. Configure Argon2id/bcrypt
   `AUTH_PASSWORD_HASHES` or `AUTH_USER_AUTHENTICATOR`. Use
   `ENABLE_DEV_EMAIL_LOGIN` only on loopback for local demos.
3. Decorate every remotely callable class with `@backend_for_frontend`.
   Undecorated classes are no longer reachable.
4. Change BFF calls with side effects to POST. Explicitly declare safe GET
   methods with `@bff_http_methods("GET")`.
5. Ensure custom cookie clients echo `pytincture_csrf` in `X-CSRF-Token` for
   POST, PUT, PATCH, and DELETE.
6. List dynamically imported browser files in `PYTINCTURE_BROWSER_FILES` and
   direct HTTP assets in `PYTINCTURE_PUBLIC_ASSET_PATHS`.
7. MCP deployments must follow the production-safe configuration described in
   the 0.10-to-1.0 migration guide; operation-ID exports are no longer supported.

## Authentication differences

`ALLOWED_EMAILS` authorizes an identity after verification; it is not proof of
identity. Production auth refuses weak/missing signing keys. Cookies default
to secure HTTPS behavior, contain fewer claims, and require CSRF on mutations.
Google, Microsoft, and SAML callbacks retain only stable identity data.

`SAML_REQUESTED_AUTHN_CONTEXT` defaults to `false` in current 0.10 releases to
support identity providers that reject forced context. Set it to `true` only
when required by IdP policy.

## Browser packaging differences

The archive is an allowlisted graph rather than a copy of the module folder.
Static local imports are discovered. Runtime-computed imports need explicit
patterns. BFF implementation bodies, private files, unrelated wheels, and
server configuration are not shipped.

Widgetsets resolve the application-declared version from PyPI first, then the
same version from the backend. `99.99.99` is only the final development
fallback. Backend resources carry a process UUID for cache invalidation;
micropip index downloads and the visible navigation URL do not.

## Verification

- log in through every enabled provider;
- call one GET-safe, one state-changing, and one streaming BFF method;
- inspect `appcode.pyt` for required dynamic files and absence of secrets;
- restart and confirm the visible application URL remains clean;
- if multiple workers are used, verify shared logout revocation through Redis.
